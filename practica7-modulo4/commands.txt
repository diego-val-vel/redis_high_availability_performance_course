Todo en un solo escenario práctico, pero dividido en fases claras.

La situación es la siguiente:

Tu equipo va a poner en producción un servicio de Redis llamado "redis-m1m3".
Este servicio será usado por varias aplicaciones:

Una parte como cache de datos de consulta.

Otra parte para guardar sesiones de usuarios.

Y otra parte para guardar contadores de operaciones importantes.

La dirección de TI te pide:

Garantizar que Redis esté configurado con una estrategia de persistencia razonable para alta disponibilidad y buen rendimiento.

Demostrar que puedes:

Hacer backups de los datos de Redis.

Restaurar los datos en caso de fallo.

Explorar el contenido de la base sin impactar el rendimiento.

Monitorear que el sistema se mantiene sano.

Probar tres modos operativos:

a) Redis con AOF como persistencia principal.
b) Redis con RDB (snapshots) como persistencia principal.
c) Redis sin persistencia, solo memoria (modo cache puro).

Mostrar qué tipo de parámetros del sistema operativo y de Redis tendrías que revisar en un entorno real para evitar:

Que el servidor se quede sin memoria.

Que el SSD sufra desgaste excesivo.

Que la latencia se dispare durante snapshots.

Tu tarea en este ejercicio es configurar ese entorno, hacer algunas operaciones básicas y documentar mentalmente (y con comandos) lo que pasa en cada caso.

Fase 1: Redis con AOF – persistencia, backup y restore
##############################

La idea es:

Crear algunos datos en Redis.

Ver dónde se guarda el AOF.

Hacer backup del AOF.

Borrar el entorno y restaurarlo usando el backup.

Paso 1.1. Insertar datos de ejemplo

Entramos al redis-cli dentro del contenedor:

# Abrir una sesión interactiva de redis-cli dentro del contenedor
/usr/bin/docker exec -it redis-m1m3 redis-cli


Dentro de redis-cli, ejecuta:

# Crear una sesión de usuario con datos básicos
SET session:1001 "user_id=1001;logged_in=true"

# Crear un contador global de pedidos
INCR orders:counter

# Simular algunos incrementos de pedidos
INCRBY orders:counter 5

# Crear una clave con TTL (ejemplo de cache de perfil de usuario)
SET user:1001:profile "{nombre: 'Ana', plan: 'premium'}" EX 3600

# Crear una lista de últimas operaciones
LPUSH user:1001:actions "login" "view_dashboard" "buy_product"

# Ver cuántos elementos tiene la lista de acciones
LLEN user:1001:actions


Comentarios uno por uno:

SET session:1001 "user_id=1001;logged_in=true"
Crea una clave que representa la sesión del usuario 1001. Útil para ver persistencia de sesiones.

INCR orders:counter
Crea o incrementa un contador de pedidos. Sirve como ejemplo de dato de negocio que no queremos perder.

INCRBY orders:counter 5
Incrementa el contador en 5, simulando varias operaciones.

SET user:1001:profile "{nombre: 'Ana', plan: 'premium'}" EX 3600
Crea un perfil de usuario con expiración de 3600 segundos. Aquí mezclamos persistencia con TTL (modo cache).

LPUSH user:1001:actions "login" "view_dashboard" "buy_product"
Inserta elementos al inicio de la lista de acciones del usuario.

LLEN user:1001:actions
Verifica cuántos elementos hay en la lista, solo para confirmar que la escritura se hizo.

Sal del redis-cli con:

# Salir de redis-cli
QUIT


Paso 1.2. Ver el archivo AOF en el host

# Ver el contenido del directorio /data dentro del contenedor (ahí vive AOF/RDB)

Comentarios:

/usr/bin/docker exec -it redis-m1m3 ls -lah /data

Ese directorio /data está mapeado al volumen redis_data en el host.

Paso 1.3. Simular un backup del AOF

El volumen redis_data es manejado por Docker. Vamos a copiar el archivo AOF desde el contenedor hacia el host como "backup lógico":

Primero identificamos el nombre del archivo AOF (normalmente appendonly.aof):

# Verifica el nombre del archivo AOF en /data
/usr/bin/docker exec -it redis-m1m3 ls /data


Supongamos que el archivo se llama appendonly.aof. Hacemos el backup:

# Crear un directorio de backups en el host
mkdir -p /home/student/redis_ha_m4/backups

# Copiar el archivo AOF desde el contenedor al host como backup
/usr/bin/docker cp redis-m1m3:/data/appendonly.aof /home/student/redis_ha_m4/backups/appendonly_backup.aof


Comentarios:

mkdir -p /home/student/redis_ha_m4/backups
Crea un directorio donde vamos a almacenar backups de Redis.

/usr/bin/docker cp redis-m1m3:/data/appendonly.aof /home/student/redis_ha_m4/backups/appendonly_backup.aof
Copia el archivo AOF desde el contenedor al host. Esto es un backup manual que puedes guardar en otro disco o nube.

Paso 1.4. Simular un desastre: borrar contenedor y volumen

Vamos a suponer que el servidor tuvo un problema y perdimos el contenedor y su volumen:

# Apagar y eliminar los servicios definidos en docker compose
cd /home/student/redis_ha_m4

# Eliminar el volumen de datos de Redis para simular pérdida completa de disco

/usr/bin/docker volume rm redis_ha_m4_redis_data

Nota: el nombre del volumen puede variar según el proyecto. Usa /usr/bin/docker volume ls si necesitas confirmar el nombre.

Fase 2: Cambiar entre AOF y RDB y hablar de tuning
##############################

En esta fase no vamos a hacer un benchmark formal, pero sí vamos a tocar la configuración para ver cómo se cambiaría la estrategia de persistencia.

Primero, actualizamos el docker-compose para usar RDB como mecanismo principal.

Paso 2.1. Versión RDB del docker-compose

Edita el archivo /home/student/redis_ha_m4/docker-compose.yml para que quede así en esta fase:

services:
  redis:
    image: redis:7-alpine
    container_name: redis-m1m3
    command:
      [
        "redis-server",
        "--appendonly", "no",
        "--save", "60", "1000"
      ]
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    restart: unless-stopped

  redisinsight:
    image: redis/redisinsight:latest
    container_name: redis-insight
    ports:
      - "5540:5540"
    depends_on:
      - redis
    restart: unless-stopped

volumes:
  redis_data:


Explicación de los parámetros:

--appendonly no
Desactiva AOF.

--save 60 1000
Configura RDB para guardar un snapshot si hubo al menos 1000 cambios en los últimos 60 segundos. Es un ejemplo relativamente moderado.

Aplicamos este cambio:

# Apagar el entorno actual
cd /home/student/redis_ha_m4
/usr/bin/docker compose down

# Eliminar el volumen de datos para empezar limpio (solo para fines del ejercicio)
/usr/bin/docker volume rm redis_ha_m4_redis_data

# Levantar el entorno con la configuración nueva basada en RDB
/usr/bin/docker compose up -d


Paso 2.2. Insertar datos en modo RDB y forzar un snapshot

# Entrar a redis-cli
/usr/bin/docker exec -it redis-m1m3 redis-cli

# Crear algunas claves de ejemplo
SET rdb:test:1 "valor1"
SET rdb:test:2 "valor2"
SET rdb:test:3 "valor3"

# Forzar manualmente un snapshot RDB
BGSAVE

# Salir de redis-cli
QUIT


Comentarios:

SET rdb:test:...
Solo son claves de prueba para que haya algo que guardar.

BGSAVE
Ordena a Redis que lance un proceso en segundo plano para generar un archivo RDB con el estado actual de la base.

Verificamos el archivo:

# Ver archivos en /data (debería existir dump.rdb)
/usr/bin/docker exec -it redis-m1m3 ls -lah /data


Aquí se ve cómo en este modo la persistencia se basa en snapshots RDB, no en un log de cambios.

Paso 2.3. Analizar a nivel conceptual el tuning durabilidad vs rendimiento

Con esto ya podemos razonar:

En AOF:

Cada comando de escritura se registra.

Más I/O, mejor RPO (pierdes poco).

En RDB:

Solo snapshots periódicos.

Menos I/O, peor RPO si los snapshots son poco frecuentes.

También podrías:

Ajustar --save a reglas más agresivas.

Rehabilitar AOF con:

--appendonly yes --appendfsync everysec

Si quisieras cambiar otra vez a AOF, la command quedaría, por ejemplo:

command:
  [
    "redis-server",
    "--appendonly", "yes",
    "--appendfsync", "everysec",
    "--save", "300", "10000"
  ]


Eso sería una combinación híbrida: RDB poco frecuente + AOF con everysec.

Paso 4.2. Ver slowlog (registro de comandos lentos)

# Configurar el umbral de slowlog (ejemplo: 10000 microsegundos = 10 ms)
CONFIG SET slowlog-log-slower-than 10000

# Ver entradas del slowlog (si las hay)
SLOWLOG GET

# Salir de redis-cli
QUIT


En este ejercicio probablemente no verás muchos comandos lentos, pero en producción es una herramienta clave de monitoreo.

Paso 4.3. OS-level tunables (conceptual)

Estos no los vamos a cambiar dentro del contenedor, pero en un host real verías cosas como:

# Ver el valor de overcommit_memory
sysctl vm.overcommit_memory

# Ver si Transparent Huge Pages está activado (en muchos sistemas)
/bin/cat /sys/kernel/mm/transparent_hugepage/enabled

# Ver el nivel de swappiness
sysctl vm.swappiness

# Ver el límite de descriptores de archivo para tu usuario
ulimit -n


Comentarios:

vm.overcommit_memory
Para Redis, suele preferirse vm.overcommit_memory=1 para evitar problemas al hacer fork para snapshots.

Transparent Huge Pages
Suele recomendarse desactivarlas para evitar pausas de latencia raras.

vm.swappiness
Si es alto, el sistema puede usar swap agresivamente, lo cual es terrible para Redis.

ulimit -n
Se debe subir para permitir muchos clientes simultáneos.

Resumen profundo y relación con Module 4: Operations

Revisemos cómo este ejercicio se conecta con todos los subtemas del módulo.

Available persistence mechanisms

En el ejercicio:

Configuraste Redis con AOF (--appendonly yes).

Luego con RDB (--appendonly no, --save 60 1000).

Luego sin persistencia (--appendonly no, --save "").

Con esto pudiste ver:

AOF: registro continuo de comandos, ideal para RPO bajo.

RDB: snapshots periódicos, menos I/O pero posible pérdida de más minutos de datos.

Sin persistencia: máximo rendimiento pero pierdes todo al reiniciar.

Precautions to avoid SSD wearout

Aunque no hicimos medidas, el ejercicio mostró:

Que AOF genera un archivo que crece con cada escritura.

Que RDB genera snapshots completos (dump.rdb).

Que puedes controlar la frecuencia de snapshots con --save.

Esto te permite razonar:

Si configuras RDB muy agresivo, escribirás el snapshot muchas veces, desgastando más el SSD.

Si usas AOF con fsync muy agresivo, tendrás muchas escrituras pequeñas al disco.

Conocer estos mecanismos es esencial para no matar la vida útil del SSD y mantener buena latencia.

Backup and restore

Practicaste:

Copiar el archivo AOF desde /data del contenedor a un directorio de backups en el host.

Simular un desastre eliminando contenedor y volumen.

Restaurar los datos copiando el backup AOF de regreso a /data y reiniciando Redis.

Esto es exactamente el flujo de backup y restore que se aplica en entornos reales (aunque allá se agregan scripts, automatización y copias a almacenamiento remoto).

Tools for exploring database contents

Usaste:

redis-cli: SET, GET, LLEN, etc.

Podrías complementar usando SCAN en lugar de KEYS para no bloquear la instancia.

RedisInsight: para ver claves, TTLs, tamaños, etc.

Explorar la base de forma segura te permite:

Entender qué tipos de datos guardas.

Detectar si hay claves gigantes o sin TTL en un entorno pensado como cache.

Tools for dump analysis

De manera sencilla:

Viste los archivos en /data (appendonly.aof, dump.rdb).

Copiaste el AOF al host y podrías analizarlo offline (tamaño, contenido, etc.).

En un entorno real:

Aplicarías herramientas específicas para leer RDB/AOF y generar reportes de:

Distribución de tipos de datos.

Top keys más grandes.

TTLs, etc.

Tuning durability vs performance

Jugamos con:

AOF activado y desactivado.

RDB con distintas reglas de save.

Sin persistencia.

Eso te permite comprender que:

Más durabilidad implica más I/O, más latencia potencial.

Menos durabilidad implica más rendimiento, pero mayor riesgo de pérdida de datos.

En producción elegirías combinaciones como:

RDB + AOF everysec para RPO bajo y arranque rápido.

Solo RDB para datos menos críticos.

Sin persistencia para caches puros.

Switching between RDB and AOF

En el docker-compose:

Cambiaste de AOF a RDB al modificar la línea command.

Podrías haber combinado ambos.

Esto muestra que cambiar la estrategia de persistencia es un cambio de configuración, pero que debe hacerse planificando:

Backups previos.

Impacto en CPU, RAM y disco por BGSAVE/BGREWRITEAOF.

Use cases for diskless Redis

La fase sin persistencia mostró:

Que tras reiniciar, las claves se pierden.

Ese comportamiento es aceptable cuando:

Redis actúa como cache.

O cuando los datos se pueden reconstruir desde otra base de verdad.

Esto te da un ejemplo práctico de por qué alguien elegiría no persistir.

Monitoring Redis performance

Usaste:

INFO (memory, clients, persistence, replication).
