-- Fase 1: Redis con AOF – persistencia, backup y restore

/*
  La idea es:

  Crear algunos datos en Redis.
  Ver dónde se guarda el AOF.
  Hacer backup del AOF.
  Borrar el entorno y restaurarlo usando el backup.
*/

-- Insertar datos de ejemplo. Entramos al redis-cli dentro del contenedor:

# Abrir una sesión interactiva de redis-cli dentro del contenedor
/usr/bin/docker exec -it redis-m1m3 redis-cli

-- Dentro de redis-cli, ejecuta:

# Crear una sesión de usuario con datos básicos
SET session:1001 "user_id=1001;logged_in=true"

# Crear un contador global de pedidos
INCR orders:counter

# Simular algunos incrementos de pedidos
INCRBY orders:counter 5

# Crear una clave con TTL (ejemplo de cache de perfil de usuario)
SET user:1001:profile "{nombre: 'Ana', plan: 'premium'}" EX 3600

# Crear una lista de últimas operaciones
LPUSH user:1001:actions "login" "view_dashboard" "buy_product"

# Ver cuántos elementos tiene la lista de acciones
LLEN user:1001:actions

# Salir de redis-cli
QUIT

/*
  Comentarios uno por uno:

  SET session:1001 "user_id=1001;logged_in=true"
  Crea una clave que representa la sesión del usuario 1001. Útil para ver persistencia de sesiones.

  INCR orders:counter
  Crea o incrementa un contador de pedidos. Sirve como ejemplo de dato de negocio que no queremos perder.

  INCRBY orders:counter 5
  Incrementa el contador en 5, simulando varias operaciones.

  SET user:1001:profile "{nombre: 'Ana', plan: 'premium'}" EX 3600
  Crea un perfil de usuario con expiración de 3600 segundos. Aquí mezclamos persistencia con TTL (modo cache).

  LPUSH user:1001:actions "login" "view_dashboard" "buy_product"
  Inserta elementos al inicio de la lista de acciones del usuario.

  LLEN user:1001:actions
  Verifica cuántos elementos hay en la lista, solo para confirmar que la escritura se hizo.
*/

-- Simular un backup del AOF

/*
  El volumen redis_data es manejado por Docker. Vamos a copiar el archivo AOF desde el contenedor hacia el host como "backup lógico":
  Primero identificamos el nombre del archivo AOF (normalmente appendonly.aof):
*/

# Verifica el nombre del archivo AOF en /data
/usr/bin/docker exec -it redis-m1m3 ls /data

-- Supongamos que el archivo se llama appendonly.aof. Hacemos el backup:

# Crear un directorio de backups en el host
mkdir -p /home/student/redis_ha_m4/backups

# Copiar el archivo AOF desde el contenedor al host como backup
/usr/bin/docker cp redis-m1m3:/data/appendonly.aof /home/student/redis_ha_m4/backups/appendonly_backup.aof

/*
  Comentarios:

  mkdir -p /home/student/redis_ha_m4/backups
  Crea un directorio donde vamos a almacenar backups de Redis.

  /usr/bin/docker cp redis-m1m3:/data/appendonly.aof /home/student/redis_ha_m4/backups/appendonly_backup.aof
  Copia el archivo AOF desde el contenedor al host. Esto es un backup manual que puedes guardar en otro disco o nube.
*/

-- Fase 2: Cambiar entre AOF y RDB y hablar de tuning

/*
  En esta fase no vamos a hacer un benchmark formal, pero sí vamos a tocar la configuración para ver cómo se cambiaría la estrategia de persistencia.

  Primero, actualizamos el docker-compose para usar RDB como mecanismo principal.
*/

-- Versión RDB del docker-compose
-- Edita el archivo /home/student/redis_ha_m4/docker-compose.yml para que quede así en esta fase:

services:
  redis:
    image: redis:7-alpine
    container_name: redis-m1m3
    command:
      [
        "redis-server",
        "--appendonly", "no",
        "--save", "60", "1000"
      ]
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    restart: unless-stopped

  redisinsight:
    image: redis/redisinsight:latest
    container_name: redis-insight
    ports:
      - "5540:5540"
    depends_on:
      - redis
    restart: unless-stopped

volumes:
  redis_data:

/*
  Explicación de los parámetros:

  --appendonly no
  Desactiva AOF.

  --save 60 1000
  Configura RDB para guardar un snapshot si hubo al menos 1000 cambios en los últimos 60 segundos. Es un ejemplo relativamente moderado.
*/

-- Aplicamos este cambio:

# Apagar el entorno actual
cd /home/student/redis_ha_m4
/usr/bin/docker compose down

# Eliminar el volumen de datos para empezar limpio (solo para fines del ejercicio)
/usr/bin/docker volume rm redis_ha_m4_redis_data

# Levantar el entorno con la configuración nueva basada en RDB
/usr/bin/docker compose up -d

-- Insertar datos en modo RDB y forzar un snapshot

# Entrar a redis-cli
/usr/bin/docker exec -it redis-m1m3 redis-cli

# Crear algunas claves de ejemplo
SET rdb:test:1 "valor1"
SET rdb:test:2 "valor2"
SET rdb:test:3 "valor3"

# Forzar manualmente un snapshot RDB
BGSAVE

# Salir de redis-cli
QUIT

/*
Comentarios:

SET rdb:test:...
Solo son claves de prueba para que haya algo que guardar.

BGSAVE
Ordena a Redis que lance un proceso en segundo plano para generar un archivo RDB con el estado actual de la base.
*/

-- Verificamos el archivo:

# Ver archivos en /data (debería existir dump.rdb)
/usr/bin/docker exec -it redis-m1m3 ls -lah /data

/*
  Aquí se ve cómo en este modo la persistencia se basa en snapshots RDB, no en un log de cambios.

  Paso 2.3. Analizar a nivel conceptual el tuning durabilidad vs rendimiento

  Con esto ya podemos razonar:

  En AOF:
  Cada comando de escritura se registra.
  Más I/O, mejor RPO (pierdes poco).

  En RDB:
  Solo snapshots periódicos.
  Menos I/O, peor RPO si los snapshots son poco frecuentes.

  También podrías:
  Ajustar --save a reglas más agresivas.

  Rehabilitar AOF con:
  --appendonly yes --appendfsync everysec
*/



-- Si quisieras cambiar otra vez a AOF, la command quedaría, por ejemplo:

-- Paso 4.2. Ver slowlog (registro de comandos lentos)

# Entrar a redis-cli
/usr/bin/docker exec -it redis-m1m3 redis-cli

# Configurar el umbral de slowlog (ejemplo: 10000 microsegundos = 10 ms)
CONFIG SET slowlog-log-slower-than 10000

# Ver entradas del slowlog (si las hay)
SLOWLOG GET

# Salir de redis-cli
QUIT

/*
  En este ejercicio probablemente no verás muchos comandos lentos, pero en producción es una herramienta clave de monitoreo.
  OS-level tunables (conceptual)
  Estos no los vamos a cambiar dentro del contenedor, pero en un host real verías cosas como:
*/

# Ver el valor de overcommit_memory
sysctl vm.overcommit_memory

# Ver si Transparent Huge Pages está activado (en muchos sistemas)
/bin/cat /sys/kernel/mm/transparent_hugepage/enabled

# Ver el nivel de swappiness
sysctl vm.swappiness

# Ver el límite de descriptores de archivo para tu usuario
ulimit -n



/*
Comentarios:

vm.overcommit_memory
Para Redis, suele preferirse vm.overcommit_memory=1 para evitar problemas al hacer fork para snapshots.

Transparent Huge Pages
Suele recomendarse desactivarlas para evitar pausas de latencia raras.

vm.swappiness
Si es alto, el sistema puede usar swap agresivamente, lo cual es terrible para Redis.

ulimit -n
Se debe subir para permitir muchos clientes simultáneos.
/*
